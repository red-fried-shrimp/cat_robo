# ROS2 STM32 小车代码逻辑

本文按当前工作区源码重新梳理，重点说明启动文件、TF 树、话题数据流、底盘安全逻辑和常见问题排查。

## 1. 当前结论

当前工程分成三种主要工作方式：

1. 手推建图模式：`slam_launch.py` 默认使用这个模式。
   - `enable_stm32=false`，默认不启动 STM32 底盘通信节点，轮子不应被 ROS2 指令驱动。
   - `use_laser_odom=true`，启动 `laser_odometry.py`，由激光数据临时估计 `odom -> base_link`。
   - `map -> odom` 由 `slam_toolbox` 动态发布。

2. 轮式里程计建图模式：`slam_wheel_odom.launch.py` 使用这个模式。
   - `enable_stm32=true`，启动 STM32 底盘通信节点。
   - `use_laser_odom=false`，关闭 `laser_odometry.py`。
   - `/odom` 和 `odom -> base_link` 由 STM32 轮速反馈积分发布。
   - `map -> odom` 仍然由 `slam_toolbox` 动态发布。

3. 正式导航模式：`nav_launch.py` 默认使用这个模式。
   - `enable_stm32=true`，启动 STM32 底盘通信节点。
   - `use_laser_odom=false`，由 STM32 轮速积分发布 `/odom` 和 `odom -> base_link`。
   - `map -> odom` 由 AMCL 动态发布。

传感器单测模式 `test_sensors.launch.py` 是安全检查用：

- 默认 `enable_stm32=false`。
- 默认发布临时静态 `map -> odom` 和 `odom -> base_link`，方便 RViz 看传感器。
- 这个模式下看到 `tf2_echo map odom` 的时间是 `0.0` 属于静态 TF，不能代表正式建图。

## 2. 推荐启动命令

### 手推建图

```bash
source install/setup.bash
ros2 launch stm32_nav_bringup slam_launch.py \
  stm32_port:=/dev/serial/by-id/usb-1a86_USB_Serial-if00-port0 \
  lidar_port:=/dev/serial/by-id/usb-Silicon_Labs_CP2102N_USB_to_UART_Bridge_Controller_f69570a8c213ec118f16f4ef7a109228-if00-port0
```

默认已经是安全手推配置，不需要再加 `enable_stm32=false use_laser_odom=true`。

如果运行后轮子还转，先急停或断底盘电源，再检查是不是手动传了 `enable_stm32:=true`，或者另一个终端还在运行导航/底盘节点。

### 轮式里程计建图

```bash
source install/setup.bash
ros2 launch stm32_nav_bringup slam_wheel_odom.launch.py \
  stm32_port:=/dev/serial/by-id/usb-1a86_USB_Serial-if00-port0 \
  lidar_port:=/dev/serial/by-id/usb-Silicon_Labs_CP2102N_USB_to_UART_Bridge_Controller_f69570a8c213ec118f16f4ef7a109228-if00-port0
```

这个模式会启动 `stm32_comm_node`，由 STM32 轮速反馈发布 `/odom` 和 `odom -> base_link`。建图前建议先把车轮架空或准备急停，确认 `/cmd_vel` 没有异常指令。

### 传感器单测

```bash
source install/setup.bash
ros2 launch stm32_nav_bringup test_sensors.launch.py
```

这个模式用于看 `/scan`、`/imu/data`、TF 是否完整。它不是正式建图。

### 正式导航

```bash
source install/setup.bash
ros2 launch stm32_nav_bringup nav_launch.py map:=/path/to/map.yaml
```

导航会启动 Nav2，Nav2 会发布 `/cmd_vel`，STM32 节点会把 `/cmd_vel` 转成串口速度指令发给底盘。

## 3. 启动文件逻辑

### `src/stm32_nav_bringup/launch/sensors.launch.py`

这是传感器和基础 TF 的公共启动文件，`slam_launch.py`、`nav_launch.py`、`test_sensors.launch.py` 都会包含它。

它负责启动：

- STM32 节点：按 `enable_stm32` 和 `use_laser_odom` 决定是否启动、是否发布 TF。
- IMU 节点：`yesense_std_ros2/yesense_node_publisher`。
- 雷达节点：`sllidar_ros2/sllidar_node`。
- 静态 TF：`base_link -> gyro_link`、`base_link -> laser`。
- 临时 TF：只在传感器单测时补 `map -> odom` 或 `odom -> base_link`。

关键条件：

| 条件 | 结果 |
| --- | --- |
| `enable_stm32=true` 且 `use_laser_odom=false` | STM32 发布 `/odom` 和 `odom -> base_link` |
| `enable_stm32=true` 且 `use_laser_odom=true` | STM32 只做串口通信和安全控制，不发布 TF |
| `enable_stm32=false` 且 `use_laser_odom=true` | 不启动 STM32，由激光里程计发布 `/odom` 和 TF |
| `enable_stm32=false` 且 `use_laser_odom=false` | 只补临时静态 `odom -> base_link`，用于单测 |

### `src/stm32_nav_bringup/launch/slam_launch.py`

建图启动文件。

默认参数：

- `enable_stm32=false`
- `use_laser_odom=true`
- `publish_identity_map_odom=false`

启动内容：

- 包含 `sensors.launch.py`
- 启动 `laser_odometry.py`
- 启动 `slam_toolbox/async_slam_toolbox_node`
- 启动 `map_saver_server`
- 启动 RViz

这里不会发布临时 `map -> odom`。正式建图时 `map -> odom` 应由 `slam_toolbox` 发布。

### `src/stm32_nav_bringup/launch/slam_wheel_odom.launch.py`

轮式里程计建图启动文件。

它会包含 `slam_launch.py`，并固定传入：

- `enable_stm32=true`
- `use_laser_odom=false`

因此它不会启动 `laser_odometry.py`，而是让 `stm32_comm_node` 接管 `/odom` 和 `odom -> base_link`。这个入口用于“雷达负责建图、STM32 轮速负责里程计”的模式。

### `src/stm32_nav_bringup/launch/test_sensors.launch.py`

传感器测试启动文件。

默认参数：

- `enable_stm32=false`
- `use_laser_odom=false`
- `publish_identity_map_odom=true`

因此它会补静态 TF：

- `map -> odom`
- `odom -> base_link`

这个模式适合检查 RViz、雷达、IMU、静态 TF，不适合判断建图质量。

### `src/stm32_nav_bringup/launch/nav_launch.py`

导航启动文件。

默认参数：

- `enable_stm32=true`
- `use_laser_odom=false`
- 必须传 `map:=...`

启动内容：

- 包含 `sensors.launch.py`
- 启动 Nav2 bringup
- 启动 AMCL
- 启动 RViz

导航模式中 `map -> odom` 由 AMCL 发布，`odom -> base_link` 默认由 STM32 轮速里程计发布。

## 4. TF 树

正常运行时 TF 应该是：

```text
map
└── odom
    └── base_link
        ├── laser
        └── gyro_link
```

各段发布者：

| TF | 手推 SLAM 发布者 | 轮式 SLAM 发布者 | 导航模式发布者 | 单测模式发布者 |
| --- | --- | --- | --- | --- |
| `map -> odom` | `slam_toolbox` | `slam_toolbox` | AMCL | 临时 static_transform_publisher |
| `odom -> base_link` | `laser_odometry.py` | `stm32_comm_node` | `stm32_comm_node` | 临时 static_transform_publisher |
| `base_link -> laser` | static_transform_publisher | static_transform_publisher | static_transform_publisher | static_transform_publisher |
| `base_link -> gyro_link` | static_transform_publisher | static_transform_publisher | static_transform_publisher | static_transform_publisher |

注意：

- 正式 SLAM 里不应该长期依赖静态 `map -> odom`。
- `tf2_echo map odom` 如果一直显示 `At time 0.0`，一般说明看到的是静态 TF。
- 正式建图时应该先确认 `/scan` 和 `/odom` 都在持续发布，再看 `map -> odom`。

## 5. 话题数据流

### 手推建图数据流

```text
sllidar_node
  └── /scan
        ├── laser_odometry.py
        │     ├── /odom
        │     └── TF: odom -> base_link
        └── slam_toolbox
              ├── /map
              └── TF: map -> odom
```

手推建图依赖雷达数据。如果 `/scan` 没有消息，`laser_odometry.py` 就不会发布 `/odom`，RViz 里的 `base_link` 也不会动。

### 轮式里程计建图数据流

```text
STM32 轮速反馈
  └── stm32_comm_node
        ├── /odom
        ├── /stm32/control_mode
        ├── /stm32/nav_state
        └── TF: odom -> base_link

sllidar_node
  └── /scan
        └── slam_toolbox
              ├── /map
              └── TF: map -> odom
```

轮式里程计建图同时依赖 STM32 串口和雷达串口。STM32 决定 `base_link` 怎么动，雷达决定地图怎么长。

### 正式导航数据流

```text
Nav2
  └── /cmd_vel
        └── stm32_comm_node
              └── STM32 串口速度指令

STM32 轮速反馈
  └── stm32_comm_node
        ├── /odom
        ├── /stm32/control_mode
        ├── /stm32/nav_state
        └── TF: odom -> base_link

/scan + /odom + map
  └── AMCL
        └── TF: map -> odom
```

## 6. STM32 节点代码逻辑

核心文件：

- `src/stm32_nav_comm/src/stm32_comm_node.cpp`
- `src/stm32_nav_comm/include/stm32_nav_comm/stm32_comm_node.h`
- 参数文件：`src/stm32_nav_bringup/config/stm32_comm.yaml`

主要功能：

1. 打开 STM32 串口。
2. 订阅 `/cmd_vel`。
3. 将 ROS2 坐标系速度转换成 STM32 坐标系速度。
4. 按 `AA CMD LEN DATA XOR 55` 协议发送速度帧和模式帧。
5. 解析 STM32 上报的轮速里程计帧。
6. 发布 `/odom`、`/stm32/control_mode`、`/stm32/nav_state`。
7. 按参数 `publish_tf` 决定是否发布 `odom -> base_link`。
8. 启动、超时、析构时发送安全停车指令。

### `/cmd_vel` 坐标转换

ROS2 坐标：

- `linear.x`：前进为正
- `linear.y`：左移为正
- `angular.z`：逆时针为正

STM32 坐标：

- `x`：右移为正
- `y`：前进为正
- `z`：逆时针为正

代码转换关系：

```cpp
stm32_vx = -msg->linear.y;
stm32_vy =  msg->linear.x;
stm32_wz =  msg->angular.z;
```

如果发现手动给 `/cmd_vel` 后方向反了，优先检查这里和下位机坐标约定是否一致。

### 安全停车逻辑

`stm32_comm_node` 有几层保护：

- 节点启动后连续发送 `MODE_ROS2 + 0速度`。
- 收到 `/cmd_vel` 时，如果 `force_ros2_mode=true`，先要求 STM32 保持 ROS2 模式。
- `/cmd_vel` 超时后周期性发送 `0速度`。
- STM32 上报非 ROS2 模式时周期性发送 `MODE_ROS2 + 0速度`。
- 节点退出析构时再补发几帧 `0速度`。

这只能降低误动作风险，不能替代物理急停。轮子异常转动时先处理电源或急停。

### 轮速里程计逻辑

STM32 上报结构体 `OdomFeedback`：

- `tick_ms`
- `control_mode`
- `nav_state`
- `omega_a`
- `omega_b`
- `omega_d`

节点用三轮角速度解算底盘速度：

- 先把轮角速度乘车轮半径得到轮线速度。
- 再解算 STM32 局部坐标速度。
- 再转换成 ROS2 坐标速度。
- 最后用 ROS 时间差积分 `x/y/yaw`。

代码里没有直接用 `tick_ms` 算 `dt`，因为当前注释说明 STM32 的 `tick_ms` 实际是 20KHz 计数器，不是毫秒。

## 7. 激光里程计代码逻辑

核心文件：

- `src/stm32_nav_bringup/scripts/laser_odometry.py`

它是手推建图模式下的临时里程计：

1. 订阅 `/scan`。
2. 把 LaserScan 极坐标转换成二维点。
3. 对相邻两帧激光做粗匹配。
4. 估计 `dx/dy/dtheta`。
5. 积分得到 `x/y/yaw`。
6. 发布 `/odom`。
7. 发布 `odom -> base_link`。

局限：

- 这是简易 scan matcher，不是成熟轮速/视觉/ICP 里程计。
- 原地旋转、走廊、空旷环境、墙面特征少时容易漂。
- 没有 `/scan` 时不会有 `/odom`。
- 如果墙体在 RViz 里旋转后漂移，优先怀疑 `/odom` 质量、雷达安装 TF、雷达数据质量。

脚本使用 `#!/usr/bin/python3`，是为了避免 conda Python 版本和 ROS Humble 的 `rclpy` 不兼容。

- `odom_topic: /odom`
- AMCL 发布 `map -> odom`。

## 9. RViz 建图步骤

1. 启动手推建图：

```bash
source install/setup.bash
ros2 launch stm32_nav_bringup slam_launch.py
```

2. 在另一个终端确认数据：

```bash
source install/setup.bash
ros2 topic hz /scan
ros2 topic hz /odom
ros2 run tf2_ros tf2_echo odom base_link
ros2 run tf2_ros tf2_echo map odom
```

3. RViz 中建议显示：

- Fixed Frame：`map`
- TF
- LaserScan：topic 选 `/scan`
- Map：topic 选 `/map`
- Odometry：topic 选 `/odom`

4. 推车动作：

- 慢速推。
- 少做长时间原地旋转。
- 先沿墙走一圈，再走回已建区域形成闭环。
- 如果墙体开始明显漂移，停下来等地图优化，不要继续快速推。

5. 保存地图：

```bash
mkdir -p ~/cat_robo/maps
ros2 run nav2_map_server map_saver_cli -f ~/cat_robo/maps/my_map
```

保存后会生成：

- `~/cat_robo/maps/my_map.yaml`
- `~/cat_robo/maps/my_map.pgm`

## 10. 常见问题排查

### 轮子一启动就转

优先处理安全：

1. 急停或断开底盘电源。
2. 确认当前不是 `nav_launch.py`。
3. 确认没有传 `enable_stm32:=true`。
4. 查是否还有旧节点在跑：

```bash
ros2 node list
ros2 topic echo /cmd_vel --once
```

手推建图应使用：

```bash
ros2 launch stm32_nav_bringup slam_launch.py
```

默认不会启动 STM32 节点。

### `/scan` 没有数据

检查 USB 设备：

```bash
ls /dev/serial/by-id/
lsusb
```

再检查雷达话题：

```bash
ros2 topic list | grep scan
ros2 topic hz /scan
```

没有 `/scan` 时，手推建图的 `/odom` 和 `base_link` 都不会正常动。

### `/odom` 没推车也一直跑

可能原因：

- 激光里程计在静止时误匹配。
- 雷达数据抖动或环境特征不足。
- 如果启用了 STM32，则可能是轮速反馈噪声或底盘还在动。

检查：

```bash
ros2 topic echo /odom --once
ros2 topic hz /odom
ros2 node list | grep -E 'laser_odometry|stm32_comm'
```

手推建图时如果静止漂移明显，说明 `laser_odometry.py` 当前环境下不够稳，建议尽量慢推，减少原地旋转，或者改用标定好的 STM32 轮速里程计建图。

### 推车但 RViz 里 `base_link` 不动

按顺序查：

```bash
ros2 topic hz /scan
ros2 topic hz /odom
ros2 run tf2_ros tf2_echo odom base_link
ros2 node list | grep laser_odometry
```

结论判断：

- `/scan` 没数据：雷达/串口/供电问题。
- `/scan` 有数据但 `/odom` 没数据：`laser_odometry.py` 没启动或崩了。
- `/odom` 有数据但 TF 没动：检查是否有重复发布 `odom -> base_link`。

### `map -> odom` 报 frame does not exist

正式 SLAM 中，`map` 要等 `slam_toolbox` 收到有效 `/scan` 和 `odom -> base_link` 后才会出现。

检查：

```bash
ros2 node list | grep slam
ros2 topic hz /scan
ros2 topic hz /odom
ros2 topic echo /map --once
```

如果只是跑 `test_sensors.launch.py`，看到静态 `map -> odom` 是为了 RViz 单测，不代表建图正常。

### 旋转后墙体漂移

常见原因：

- 激光里程计原地旋转估计不准。
- 雷达安装角度或 `base_link -> laser` 静态 TF 不符合实际。
- 雷达点云质量差，反光/玻璃/远距离空旷导致匹配不稳。
- 建图时推得太快或原地旋转太多。

建议：

1. 先确认 `/scan` 在 RViz 中方向正确。
2. 检查雷达实际安装位置是否真的是 `x=0 y=0 z=0.54409 yaw=0`。
3. 手推时多做平移，少做原地旋转。
4. 如果要长期稳定建图，优先使用标定好的 STM32 轮速里程计，或者替换成成熟的激光里程计算法。

## 11. 快速自检清单

建图前先跑：

```bash
source install/setup.bash
ls /dev/serial/by-id/
ros2 launch stm32_nav_bringup slam_launch.py
```

另开终端：

```bash
source install/setup.bash
ros2 topic hz /scan
ros2 topic hz /odom
ros2 run tf2_ros tf2_echo odom base_link
ros2 run tf2_ros tf2_echo map odom
```

正常现象：

- `/scan` 有频率。
- `/odom` 有频率。
- 推车时 `odom -> base_link` 会变化。
- `slam_toolbox` 工作后 `map -> odom` 出现。
- RViz 中 `/map` 会逐渐生成。

异常现象：

- `/scan` 没频率：先查雷达 USB。
- `/odom` 没频率：先查 `laser_odometry.py` 或 STM32 节点。
- `base_link` 不动：查 `/odom` 和 `odom -> base_link`。
- 墙体漂：查里程计质量、雷达 TF、推车方式。
- 轮子转：先急停，再查是否启动了 STM32 或 Nav2。
